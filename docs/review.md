## 长案例失败归因与处置（本轮）

对上一轮 6 次失败逐条归因。前 5 次发生在提示词补齐之前，原因是 DeepSeek 的 JSON 模式不在服务端强制 schema，而提示词尚未写明校验器真正强制的两条硬约束（痛点字段精确集合、等级枚举），属于提示词缺陷，已由 schema 与枚举声明修复。

第 6 次（品牌长文档角色证据不可回溯）已定位到诱因：附录由 51 个结构近乎相同的小节构成（标题模板相同、角色句逐字重复 51 次、任意两段最高相似度 0.997），且语料混用「销售团队」与裸角色列表「市场、设计、门店」两种命名风格，模型在重复语境下改写角色证据。据此完成三项处置并全部由自动化测试覆盖（不依赖再次付费调用）：按条丢弃无法回溯的摘录并在页面/报告披露、结构与等级不符仍整份拒绝；空白归一化保留换行结构，跨行拼接不再算原文；校准脚本新增 `--dump-rejected`（写入被 Git 忽略的 `runtime/rejected/`，生产路径仍不落盘模型输出）。

这些改动改变的是失败后的处置，不是模型通过率；3/9 的通过率仍是当前唯一的真实联调数据。长案例是否稳定仍需新的付费校准，未测不得声称。

上述改动的回归验证并入上方「当前验证」一节，未单独重复计数。

已知未处理的残留：`DIAGNOSIS_SCHEMA` 仍未声明 `evidence` 数组的 `minItems`，因此「每条事实/痛点至少一条证据」只由应用端保证，OpenAI 严格模式也不会据此约束解码。现在应用会把空证据条目按条丢弃并披露，所以这是输出质量残留而非正确性缺陷。补声明会改动发给模型的 schema 文本、使现有 3/9 校准记录不再可比，因此留待下一次真实校准一并验证。
